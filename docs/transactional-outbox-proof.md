# 3.8.4.2: transactional Keycloak outbox proof

Branch: `fix/transactional-identity-outbox`. Scope is a disposable source proof,
not a production identity-event rollout. The provider is packaged only by
`docker/keycloak/Dockerfile.outbox-test`, selected by the existing runtime test
Compose file. Production `Dockerfile` and `compose.runtime.yaml` are unchanged.
No real realm is automatically configured with the proof listener.

## Build and ownership

Java 21/Maven 3.9.11 builds against Keycloak **26.8.1** with provided dependencies;
the JAR does not bundle a second Keycloak runtime. Both build/runtime base images
have immutable digests. Python remains configuration/test tooling.

The `identity-outbox` JPA provider has a versioned Liquibase changelog which
creates only integration-owned tables through the pinned Keycloak entity manager:

- `dl_identity_revision`: primary key `(realm_id, subject)`, nonnegative BIGINT
  profile/security counters. Profile writes use an atomic PostgreSQL upsert with
  `RETURNING`; concurrent increments lock the same database row. Security starts
  at zero; security-event allocation/mappings are not implemented yet.
- `dl_identity_outbox`: UUIDv4 event primary key, realm, subject, bounded JSON
  payload and creation time. Index `(created_at_ms, event_id)` supports later
  publisher traversal. No account foreign key: pending intent survives account
  deletion. No passwords or token/session storage.

There is no direct SQL modification or dependency on Keycloak-managed tables.
No publisher, published marker, delivery receipt or retention job is created by
this proof. Those require later versioned integration migrations.

## Transaction behavior

The `identity-outbox-proof` event listener reads canonical model display fields,
never raw admin representations. Administrator user creation/update emits the
existing v1 create/profile contracts. The initial registration handler is not
acceptance-tested yet; full user/security mappings remain 3.8.4.3 work.
Do not enable this incomplete proof listener on development/team/cloud realms.

Revision increment, model mutation and outbox insertion use one transaction.
`persist`/`flush` happens before success; no external broker call occurs there.
Combined names and other display fields must fit the contract; failures roll
back instead of publishing invalid snapshots. Payloads have a 16,384-byte bound
in both code and the database. Event identity is persisted, not regenerated by
future retrying senders. Counters are not processing timestamps.

Keycloak catches listener exceptions. Setting rollback-only by itself was found
to permit a misleading HTTP 204 after rollback in the pinned administrator update
path. A failing transaction-prepare participant now propagates failure before
main transactions commit, and the transaction is also marked rollback-only.
Tests must check both the API response and persisted state. Do not infer success
from a swallowed listener exception or weaken this to best-effort logging.

The proof currently uses one revision row per affected account. It introduces no
process-only lock, generic transaction retry framework or model/tool retry.
Broader lock ordering and source/security-event concurrency remain part of the
next mapping stage. No claim of guaranteed deadlock freedom is made.

## Acceptance gate

The real `tests/test_outbox_transaction.py` runs against disposable PostgreSQL,
Keycloak and synthetic administrator/accounts. It checks:

1. Account creation commits with one schema-valid snapshot.
2. Four concurrent profile updates get unique consecutive revisions; security
   counters remain unchanged.
3. An oversized combined display name rejects the mutation and preserves state.
4. A temporary integration-table constraint forces immediate outbox failure;
   account, event count and source revision must roll back together.
5. A disposable deferred constraint trigger fails at commit, after listener
   flush succeeded; neither new account nor its outbox/revision may persist.
6. A subsequent valid update has no committed revision gap. Account deletion
   and a Keycloak restart preserve the exact pending payloads/event IDs.

Only synthetic integration tables receive fault-injection constraints/triggers,
which are removed in `finally`. No fault controls are added to the provider.
The full identity CI gate uses this image and discovers the test automatically.
Final fresh-stack gate on **10 November 2026: 156 passed in 435.03 seconds**.
The ignored `test-results/identity-outbox.xml` report confirms zero failures,
errors or skipped tests. Focused atomic proof passed in 45.82 seconds; the
separate unit gate had 134 passes and 22 runtime/PostgreSQL tests deselected.
Pinned Maven/Java compilation and Keycloak augmentation succeeded. Ruff lint,
changed-file formatting, dependency and Git whitespace checks passed. Required
remote PR `tests` and delivery remain pending; no commits/pushes were made.
The earlier interrupted gate had no captured final result and was not counted
as a pass. Verification used fresh disposable containers, not retained bootstrap
accounts from earlier runs. Production image and real realms remain unchanged.

For a full local gate, recreate only the disposable project first, as CI does:
the bootstrap acceptance test intentionally retains a fixed administrator to
verify persistence and cannot simply be rerun against its previous database.
From this repository, with Docker running:

```powershell
docker compose -p datalens-identity-tests -f compose.test.yaml -f compose.runtime.test.yaml down
docker compose -p datalens-identity-tests -f compose.test.yaml -f compose.runtime.test.yaml up -d --build --wait --wait-timeout 180
$env:IDENTITY_DATABASE_TESTS = '1'
$env:IDENTITY_RUNTIME_TESTS = '1'
python -m pytest -q
docker compose -p datalens-identity-tests -f compose.test.yaml -f compose.runtime.test.yaml down
```

These commands must use the exact disposable project/files above, never a
development Compose project or volume. No `--volumes` flag is needed for tmpfs.

The first full regression run had 155 passes and one existing lifecycle-test
failure. Its short-session wait subtracted host wall time from server token
expiry; the disposable VM clock was measured about 4.45 seconds behind Windows.
The test now asserts a positive server-issued lifetime of at most three seconds
and waits that duration plus the existing two-second margin. It still requires
refresh rejection with HTTP 400. The isolated corrected lifecycle gate passed
in 65.63 seconds; production token validation and provider lifetimes are unchanged.

## Boundaries and upgrade risk

Custom JPA entity support is explicitly an unsupported/internal Keycloak API;
`getEntities()` is deprecated in the pinned version. A successful proof on 26.8.1
does not establish compatibility with another release. Rebuild and rerun these
gates before changing the version. Removing the proof JAR does not delete its
tables; this step performs no destructive contraction or live migration.

Mandatory password-change logout, complete source mapping, RabbitMQ publishing,
agent consumers, CORS and hosted deployment remain pending. Stop before 3.8.4.3.
